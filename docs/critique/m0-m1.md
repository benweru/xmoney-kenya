# Critique: M0 and M1

**Scope**: PRs #1–#8 (the foundation, the monorepo, dev tooling, sign-in, STK top-ups, P2P transfers, wallet privacy, and history), read at the head of `transaction-history`. Written 13 Oct 2026, while #4–#8 were waiting to merge.

## Ordinary

None of this is a weakness, but none of it is a differentiator either:

- FastAPI, SQLAlchemy, and Alembic with a typed config, ruff, strict mypy, and pre-commit.
- Phone-and-PIN sign-in with Argon2, an OTP inbox, httpOnly cookies, and a lockout after wrong PINs.
- Keyset (cursor) pagination for history, and owner-only wallet reads. Getting these right is expected. The tie-breaker test is a nice touch.
- Idempotency keys on write endpoints. Every payments tutorial has them now.

## Genuinely impressive

- **The database enforces the ledger, not just the app.** A deferred trigger rejects unbalanced entries, and postings cannot be updated (migrations 0001 and 0002). A bug in Python cannot create or destroy money silently.
- **Idempotency keys are bound to a request hash.** Reusing a key with a different body returns 409 instead of replaying the wrong answer (`ledger/service.py` `_assert_same_request`, and the same pattern in transfers and top-ups). Many production APIs get this wrong.
- **Callback races are handled, not hoped away.** A callback can arrive before the STK Push response. It is logged as unmatched and applied once the `CheckoutRequestID` is known (`payments/topups.py` `_apply_early_callback`). `expired` means "we stopped waiting", so a late success still credits the wallet. A Postgres trigger enforces the same state table.
- **Concurrency is designed.** Accounts are locked in id order, so A → B racing B → A cannot deadlock. The balance is checked under those locks, and 100 concurrent sends never overdraw.
- **The tests were mutation-checked by hand.** Removing the top-up row lock makes the concurrency test fail (10 applied instead of 1), and dropping the entry id from the cursor loses entries. Few people do this. It is not yet written up anywhere a reviewer will see it.
- CI runs `alembic check` and a full downgrade and re-upgrade, so migration drift is caught.

## Weakest parts, ranked

1. **A success callback mints money on the URL token alone.** `handle_stk_callback` credits the wallet whenever the path token matches and the payload says `ResultCode 0` (`payments/topups.py` `_apply`). The token is a static secret in a URL. It ends up in access logs, CloudFront logs, and any proxy along the way, and it never rotates. Anyone who has it can forge a callback for any pending `CheckoutRequestID`, and the CheckoutRequestID is returned to the user in the top-up response. There is no IP allowlist (planned for M5) and no confirmation with STK Query before crediting. In sandbox, the cost is fake shillings. In an interview, the question is "how do you know M-PESA sent this?", and today the answer is "a shared string". This becomes urgent in M2, when the callback URL goes public.
2. **One global hot row, and balances that get slower over time.** Every top-up posts against `mpesa_float`, and `_lock_accounts_and_post` takes `FOR UPDATE` on every account in the entry. So all top-ups across all users run one at a time. Every balance read is a `SUM` over all of the account's postings (`_account_sums`), and the float account's sum grows with every top-up. The load test will find both. The ledger is correct, but its throughput is capped by design, and the cap shrinks as history grows.
3. **Disputed answers go nowhere.** `AMOUNT_MISMATCH` and `CONFLICT` callbacks are logged, but no one is alerted and nothing reaches a queue. Worse, an amount-mismatch top-up stays pending, and a later STK Query success carries no amount (`RailResult.amount_cents is None`), so `resolve_topup` then credits the *requested* amount and ignores the mismatch evidence already on file. The stale-top-up resolver (`payments/resolve.py`) is a script that nothing schedules yet. These gaps are expected before M3, but they should be named.
4. **The evidence is invisible.** There are no coverage numbers, no property-based tests, and no published mutation results. The invariants are tested with examples, not generated sequences. A reviewer has to read test files to believe the claims.

## What would raise the bar next

1. Credit a wallet only after STK Query confirms the callback, and add a test that a forged success callback with the correct token credits nothing. (One PR, after `aws-infra`.)
2. Hypothesis properties for the ledger (debits and credits of all postings equal, no negative wallet, replays add no postings), plus a published coverage table and the "broke it on purpose" write-up.
3. Stop locking system accounts that may go negative, and add a running balance per account that a trigger maintains and the reconciler checks. Prove the gain with the M3 load-test row.
