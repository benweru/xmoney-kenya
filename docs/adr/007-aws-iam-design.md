# 007. AWS IAM: OIDC deploys, one role per job, and secrets per task

- Status: Accepted
- Date: 2026-10-13

## Context

[ADR 003](003-aws-hosting-terraform-later.md) chose AWS and deploys from CI with no long-lived keys, and left the details to the first deploy. The Terraform in `infra/terraform/` now defines them. The demo is public and sandbox-only. Even so, a leaked credential could run up a bill or read the Daraja sandbox keys. So every principal gets only what its job needs, and IAM is an area this project is meant to show.

Principals:

- **People**: Ben, applying Terraform from a laptop.
- **GitHub Actions**: shipping images and web files on every merge to `main`.
- **ECS**: starting each task (the *execution* role) and the code running inside it (the *task* role).
- **EventBridge Scheduler**: starting the two scheduled jobs.

## Decision

- **People use IAM Identity Center**, not IAM users or the root user. The [first-deploy runbook](../runbooks/aws-first-deploy.md) sets this up: root has MFA and no access keys, and one admin permission set is used for `terraform apply` through short-lived `aws sso login` sessions.
- **GitHub uses OIDC.** The role `xmoney-demo-github-deploy` trusts `token.actions.githubusercontent.com`, but only for the subject `repo:benweru/xmoney-kenya:environment:demo`. A fork, a pull request, or a workflow outside the `demo` environment cannot assume it, and the `demo` environment can require a reviewer.
- **The deploy role can ship, not build infrastructure.** It can:
  - push to the one ECR repository;
  - register task definitions;
  - update the one ECS service;
  - repoint the two schedules;
  - pass only the task and scheduler roles the stack created;
  - sync the one web bucket;
  - invalidate the one distribution;
  - read the one SSM parameter that names all of these.

  It cannot change networking, IAM, RDS, or security groups. Those changes go through a person running `terraform apply`. The ECR part lives in `foundation` and the rest in `app`, scoped to that stack's actual ARNs, so `make aws-down` removes the app part too.
- **Separate execution roles per kind of task.** The API's execution role can read the database secret, the STK callback token, and (only when the sandbox rail is on) the Daraja secret. The jobs' execution role reads the database secret and, when the sandbox rail is on, the Daraja secret. It never reads the callback token. Both can pull only the API image and write only to their own log group.
- **Task roles exist but grant nothing.** The code calls no AWS APIs, so a compromised container gets no AWS permissions. The roles exist so a future need, such as KMS for M4's envelope encryption, gets added to one role on purpose.
- **Scheduler gets one role.** It can call `ecs:RunTask` only on the two job families, only in this cluster, and pass only the jobs' roles.
- **Three secrets, each with a different owner:**
  - Database: generated by Terraform, ephemeral and write-only, so it is never in state.
  - STK callback token: generated by Terraform. It is in state, and it is low value because Daraja sees it in every push.
  - Daraja sandbox keys: created empty by Terraform and filled by hand, so they are never in state.
- Every trust policy for an AWS service checks `aws:SourceAccount`, and every `iam:PassRole` checks `iam:PassedToService`.

## Consequences

- No AWS key exists in GitHub or in the repository. The only GitHub configuration is two repository variables: the role ARN, which is not a secret, and the region.
- A compromised GitHub workflow in the `demo` environment can deploy a malicious image. That is inherent to CD. The mitigations are the environment's required reviewers and branch rules.
- Infrastructure changes are manual applies, not CI. That is deliberate at this size, and a later milestone could add a plan-only role for pull requests.
- The database password does not rotate on its own. An RDS-managed secret would rotate every 7 days and break running tasks until they restart. Bumping `db_password_version` and redeploying rotates it by hand.
- None of this has been applied yet. The first apply may surface a missing permission, for example in the deploy workflow's `RegisterTaskDefinition` call. Fix it narrowly in `deploy.tf` rather than widening the policy to `*`.

## Alternatives considered

- **An IAM user with access keys in GitHub secrets.** These are long-lived, keys leak, and ADR 003 already rules it out.
- **Letting CI run `terraform apply` with a broad role.** It removes drift, but the deploy role would then need near-admin rights.
- **One execution role for all tasks.** Simpler, but every job could read every secret.
- **RDS-managed master password (`manage_master_user_password`).** It keeps the password out of state too, but its forced rotation would need a restart hook. Revisit once tasks read the secret at connect time.
